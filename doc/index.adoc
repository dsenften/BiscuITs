*Abstract*

BiscuITs ist eine KI-gestützte Microservice-Architektur zur Verarbeitung von Dokumenten und Adressdaten. Die Anwendung verwendet {docling}[Docling] für die intelligente Dokumentenverarbeitung, {openai}[OpenAI] für die KI-Funktionalitäten und {rabbitmq}[RabbitMQ] für die asynchrone Kommunikation zwischen den Services. Die Benutzeroberfläche basiert auf {streamlit}[Streamlit] und ermöglicht die einfache Eingabe und Visualisierung von Daten.

--


== Überblick

BiscuITs ist eine modulare, KI-gestützte Anwendung zur Verarbeitung von Dokumenten und Adressdaten. Die Architektur basiert auf Microservices, die über einen zentralen Message Broker kommunizieren und in separaten Docker-Containern bereitgestellt werden. Es gibt zwei Hauptfunktionsstränge:

1. **Dokumentenverarbeitung**: Ermöglicht das Hochladen, Analysieren und Abfragen von Dokumenten mit KI-Unterstützung
2. **Adressdatenverarbeitung**: Ermöglicht die Analyse und Validierung von Adressdaten

  ** `result_processor_input`: Address Analyzer/Document Processor → RabbitMQ → Result Processor Service
  ** `ui_updates`: Result Processor Service → RabbitMQ → UI

  ** OpenAI API für KI-Funktionalitäten
  ** RabbitMQ-Konfiguration für alle Services
  ** Docling-Integration für Dokumentenanalyse

  ** Alle Komponenten laufen in separaten Docker-Containern
  ** Definierte Ports für externe Kommunikation
  ** Gemeinsames Netzwerk für Container-Kommunikation

== Ablauf

.Sequenzdiagramm
[mermaid, sequence-diagram, svg]
----
include::images/sequence-diagram.mermaid[width=60%]
----

Das Sequenzdiagramm zeigt zwei parallele Abläufe im System - die Adressdatenverarbeitung und die Dokumentenverarbeitung:

1. **Initialisierungsphase**:
  ** Alle Komponenten deklarieren ihre benötigten Queues bei RabbitMQ:
     *** UI: `ui_updates`, `address_analyzer_input`
     *** Document Service: `document_processor_input`
     *** Document Processor Service: `document_processor_input`, `result_processor_input`
     *** Address Analyzer Service: `address_analyzer_input`, `result_processor_input`
     *** Result Processor Service: `result_processor_input`, `ui_updates`

2. **Ablauf der Adressdatenverarbeitung**:
  ** Die UI sendet Adressdaten (Name, Adresse) an die `address_analyzer_input`-Queue
  ** Address Analyzer Service empfängt und verarbeitet diese Daten
  ** Address Analyzer Service sendet die Ergebnisse an die `result_processor_input`-Queue
  ** Result Processor Service empfängt die Ergebnisse und bereitet sie für die UI auf
  ** Result Processor Service sendet das Endergebnis als JSON an die `ui_updates`-Queue
  ** Die UI empfängt das Endergebnis und zeigt es in formatierter Form an

3. **Ablauf der Dokumentenverarbeitung**:
  ** Die UI sendet ein Dokument direkt an den Document Service via HTTP
  ** Document Service speichert das Dokument und sendet Metadaten an die `document_processor_input`-Queue
  ** Document Processor Service empfängt die Metadaten und führt KI-gestützte Analysen durch
  ** Document Processor Service extrahiert Inhalte, erstellt Embeddings und generiert Zusammenfassungen
  ** Document Processor Service sendet die Analyseergebnisse an die `result_processor_input`-Queue
  ** Result Processor Service empfängt die Ergebnisse und bereitet sie für die UI auf
  ** Result Processor Service sendet das Endergebnis als JSON an die `ui_updates`-Queue
  ** Die UI empfängt das Endergebnis und zeigt es in formatierter Form an

Dieses Diagramm verdeutlicht die asynchrone, ereignisgesteuerte Kommunikation zwischen den Komponenten und die zentrale Rolle von RabbitMQ als Message Broker. Beide Verarbeitungspfade verwenden ähnliche Kommunikationsmuster, nutzen aber unterschiedliche spezialisierte Microservices für die jeweiligen Domänen.

== Komponenten

=== Streamlit UI

==== Beschreibung

{streamlit}[Streamlit]-basierte Webanwendung, die als zentrale Benutzerschnittstelle dient. Die Anwendung bietet zwei Hauptfunktionen: Adressdatenverarbeitung und Dokumentenupload. Sie kommuniziert über RabbitMQ mit den Backend-Services und zeigt die Verarbeitungsergebnisse in formatierter Form an.

==== Funktionen

===== Benutzeroberfläche
* Tab-basierte Navigation zwischen verschiedenen Funktionen
* **Adressdaten-Tab**:
  ** Eingabefelder für Name, PLZ, Ort und Straße
  ** Formular-basierte Dateneingabe
  ** Statusanzeigen für Verarbeitungsprozess
  ** JSON-Anzeige für strukturierte Ergebnisse
* **Dokumente-Tab**:
  ** Drag-and-Drop Datei-Upload für verschiedene Dokumenttypen (PDF, TXT, DOC, DOCX, JPG, PNG)
  ** Vorschau der hochgeladenen Dateien
  ** Verarbeitungsstatus-Anzeigen

===== Kommunikation
* RabbitMQ-Integration für asynchrone Verarbeitung
* Retry-Mechanismus für robuste Verbindungen
* Timeout-Handling (30 Sekunden)
* HTTP-Verbindung zum Document Service

==== Nachrichtenformate

Ausgehend (Adressdaten):
[source,json]
----
{
    "name": "string",
    "address": "string",
    "timestamp": "float"
}
----

Ausgehend (Dokumentendaten):
[source,json]
----
{
    "document_id": "string",
    "file_path": "string",
    "file_type": "string",
    "timestamp": "float"
}
----

Eingehend (Verarbeitungsergebnisse):
[source,json]
----
{
    "type": "string",  // "address" oder "document"
    "status": "string",  // "completed", "error", "processing"
    "data": {
        "name": "string",  // bei Adressdaten
        "address": "string",  // bei Adressdaten
        "document_id": "string",  // bei Dokumentendaten
        "details": "string",
        "timestamp": "float"
    },
    "error": "string"  // optional, bei Fehlern
}
----

==== Queues

* `address_analyzer_input`: Sendet Adressdaten an Address Analyzer Service
* `ui_updates`: Empfängt Verarbeitungsergebnisse von allen Services

==== Fehlerbehandlung

* Validierung der Eingabefelder mit benutzerfreundlichen Warnungen
* Robuste RabbitMQ-Verbindungen mit Retry-Logik und Logging
* Timeout-Überwachung bei Antworten
* JSON-Parsing von Antworten mit Fallback-Mechanismus
* Benutzerfreundliche Fehleranzeigen für verschiedene Fehlertypen

== Deployment

=== Docker-basiertes Deployment 

Alle Komponenten der Anwendung werden in Docker-Containern bereitgestellt und mit Docker Compose orchestriert. Dieses Vorgehen bietet mehrere Vorteile:

* Isolierte Ausführungsumgebungen für jeden Service
* Konsistente Entwicklungs- und Produktionsumgebungen
* Einfaches Skalieren einzelner Komponenten
* Zentrale Konfiguration aller Services
* Gemeinsames Netzwerk für die Container-Kommunikation

Die Konfiguration aller Services erfolgt in der Datei `docker-compose.yml`. Jeder Service erhält dabei:

* Ein eigenes Container-Image, basierend auf einem Dockerfile im jeweiligen Service-Verzeichnis
* Konfigurierbaren Zugriff auf Umgebungsvariablen
* Spezifische Ports (falls benötigt)
* Volumenmounts für persistente Daten (z.B. für hochgeladene Dokumente)

=== Start der Anwendung

Zum Starten der Anwendung muss lediglich der folgende Befehl ausgeführt werden:

[source,bash]
----
docker compose up
----

Für die Ausführung im Hintergrund kann der Parameter `-d` hinzugefügt werden:

[source,bash]
----
docker compose up -d
----

Für die lokale Entwicklung können die Services auch ohne Docker ausgeführt werden. Dazu müssen die folgenden Voraussetzungen erfüllt sein:

== KI-Integration mit Docling

=== Über Docling

{docling}[Docling] ist ein Framework für dokumentenzentrierte Sprachverarbeitung, das die Erstellung von KI-gestützten Dokumentenanwendungen vereinfacht. Es integriert sich nahtlos mit gängigen KI-Modellen, um folgende Funktionen zu ermöglichen:

* Dokumentenextrahierung und -konvertierung
* Intelligentes Text-Chunking
* Vektoreinbettungen für semantische Suche
* Dokumentenanalyse und -zusammenfassung

=== Integration in BiscuITs

BiscuITs nutzt Docling für die intelligente Dokumentenverarbeitung im Document Processor Service. Die Integration umfasst:

1. **Dokumentenkonvertierung**: Extraktion von Text aus verschiedenen Formaten
2. **Hybrides Chunking**: Intelligente Aufteilung von Dokumenten in sinnvolle Abschnitte
3. **Embedding-Generierung**: Erstellung von Vektorrepräsentationen mit OpenAI-Modellen
4. **Suche**: Semantische Suche über Dokumente mittels LanceDB
5. **Chat**: KI-gestützte Beantwortung von Fragen zu Dokumenteninhalten

=== Beispielimplementierung

Im Verzeichnis `example/docling` befindet sich eine vollständige Beispielimplementierung, die den Gesamtprozess demonstriert:

* `1-extraction.py`: Dokumentenextraktion aus PDF-Dateien
* `2-chunking.py`: Intelligentes Aufteilen von Dokumenten
* `3-embedding.py`: Erstellung von Vektoreinbettungen
* `4-search.py`: Semantische Suche über Dokumente
* `5-chat.py`: KI-gestützte Frage-Antwort zu Dokumenten

Diese Beispiele dienen als Referenz für die Integration in die Microservices.
